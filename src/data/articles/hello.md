ScaleKit 做了 75 次测试，比较 CLI 和 MCP 哪个更适合 AI Agent 执行任务。结果 CLI 在所有效率指标上都赢了：成本便宜 10 到 32 倍，而且成功率是 100%；MCP 的成功率只有 72%。

如果事情真的就这么简单，那这篇文章三段话就能讲完：用 CLI，加一个 skills 文件，然后就结束了。

但是，ScaleKit 现在做的不是只帮开发者完成自动化流程，而是在做能替客户的用户、**在客户公司的系统里执行操作的 Agent**。它会连接客户控制的第三方服务，比如 GitHub、Jira、Slack 等。

一旦场景从：`我自己用 AI Agent 自动化完成自己的工作`，

变成：`我的 Agent 产品帮助客户自动化完成他们公司的工作`

CLI 原本那些高效、便宜、直接的优点，就**可能反过来变成系统架构上的风险和麻烦。**

毫无疑问，**CLI 或者 MCP 都可以替 Agent 完成外部世界的工作**，但是 CLI 和 MCP **不是对立关系**，当场景不同时，我们的选择也会不同。下面先介绍 MCP 作为个人开发者工具时的缺点，然后下一部分再介绍，究竟什么场景才会用到 MCP。





# 上下文膨胀

比如 github 的 MCP 服务器暴露了 43 个工具。每当 Agent 发起一次工具调用时，所有 43 个工具的完整 schema（工具描述和工具定义）都会成为对话上下文的一部分。对于一个简单的“获取仓库信息”调用来说，Agent 还要携带用于创建 gist、管理 pull request review、配置 webhook 等工具的 schema——这些工具它根本不会用到。

CLI Agent 没有这个问题。它已经从训练数据中了解 gh。它可以一次性组合出正确的命令。没有 schema 开销。没有发现工具的步骤。

800 token 的技巧：一个带有 skill 增强的 CLI——也就是一份仅包含 gh 使用技巧的 800 token 文档——相比朴素的 CLI，可以减少三分之一的工具调用，并将延迟降低三分之一。这是整个基准测试中投资回报率最高的做法。任何团队今天都可以应用它。



> **MCP 会占用大量的上下文，而 CLI 不会**



# 规模化场景

做同样的事情，每个月的成本一个是 3.20 美元，另一个是 55.20 美元。

如果按 Claude Sonnet 4 的价格来算，每个月执行 1 万次操作：

```txt
1. CLI： 大概要花 3.20 美元
2. 直接用 MCP： 大概要花 55.20 美元
3. 如果 MCP 经过 Gateway 做了 schema 过滤：大概要花 5 美元
```

这意味着 MCP 的成本放大了 17 倍，而且还额外有 28% 的失败率。

> **MCP 会将成本无限扩大，而 CLI 相对来说非常便宜**



看到这里，CLI 看起来几乎是全面胜出：更便宜、更稳定、也更简单。

如果你只看到这里，很可能会觉得：MCP 好像没什么必要，它像是先有了一个协议，然后再去找适合它解决的问题。

如果这个 Agent 只是给你自己用的，毫无疑问 CLI 肯定比 MCP 要好。**但对于其他任何场景来说，这个结论都会是危险的错误。**



# 很多人没看到的关键部分

重点不是纠结到底用 CLI 还是 MCP，而是要先搞清楚：**这个 Agent 到底是谁在用**？
是你自己在用？还是你把这个 Agent 做出来，给你的甲方用（你的客户在用）？

现在大家拿 CLI 和 MCP 做对比测试，包括我们自己的测试，其实**测的都是同一个场景**：**一个开发者用 AI Agent 自动处理自己的工作。**在这种情况下，CLI 当然更好。因为 Agent 用的是你自己的账号和权限，**出了问题也只影响你自己**。

但真正上线的 AI 产品，大多数不是“开发者自己用工具”这种场景。
如果你做的是 B2B SaaS（部署在云端，使用这个 Agent 的人，是你的客户）、项目管理工具、客服系统、代码审查助手，那么这个 Agent 不是在替你干活，而是在替客户公司的员工干活。它会进入客户公司的组织环境，访问客户的数据，并连接客户控制的各种服务。

![图片1](/images/articles/hello-1.png)

假设你在做一个项目管理平台里的 AI 助手。
Acme 公司的一名员工对这个 Agent 说：“根据这个 GitHub PR 创建一个 Jira 任务，然后在 Slack 里通知团队。”
这时你的 Agent 要做三件事：

```txt
读取 Acme 的 GitHub PR
在 Acme 的 Jira 里创建工单
在 Acme 的 Slack 里发通知
```

而且它必须使用这个员工自己的权限，只能访问 Acme 公司的数据，绝对不能把内容发到 Globex 公司的 Jira，或者 Initech 公司的 Slack。

也就是说，Agent 每做一个动作，**你的 Agent 后端都要同时搞清楚三件事：**

1. **Agent 是谁**。到底是哪一个 Agent 发起的请求？这样才能限制它的调用频率、防止它乱用系统，并且后面出问题时能查日志。
2. **用户是谁**。是谁允许 Agent 做这件事？Agent 不能想干什么就干什么，**只能做这个用户自己有权限做的事情。OAuth 的权限范围会限制它。**
3. **用户属于哪家公司**。这个用户是 Acme 的人，还是 Globex 的人？Acme 的 GitHub 仓库信息，绝对不能跑到 Globex 的 Jira 里。这里一旦弄错，就不是小错误，而是数据泄露。



## **现在你试试看，只靠 `gh auth login` 能不能处理这种复杂身份关系**



* **一个凭证，多个用户**

  当你运行 `gh auth login` 时，你的 Agent 会继承你的个人 token。一个凭证，一个用户。现在这个 Agent 不是给你个人使用，Agent 的用户扩展到三个组织，每个组织都有几十个用户，而且每个用户在 GitHub、Jira 和 Slack 上都有不同的权限级别。

  CLI 的登录方式适合“一个人自己用”，**不适合“一个产品服务很多客户和很多用户”**。
  CLI 的登录方式很简单，因为它默认只有一个人用：你登录，你操作，你承担风险。

  但 B2B 产品（你的 Agent 是给多个公司用的）里有很多公司、很多用户。Agent 不能总用你的 GitHub token，**它必须根据当前请求切换成“这个公司、这个用户”的权限**。比如 Acme 的用户 A 发起请求，就必须用用户 A 的权限；Globex 的用户 B 发起请求，就必须用用户 B 的权限。

  **如果你硬要用 CLI 来做，就要自己管理一堆 token、切换 token、刷新 token、防止串用 token。**这样会把原本应该由 OAuth / 平台协议处理的事情，变成你自己后端里的复杂安全系统。

  > 总结，如果这个 Agent 有很多人使用，在身份认证的场景下：
  >
  > * 如果硬要使用 CLI 的方式来进行身份认证，我们就必须得自己实现复杂的安全系统
  > * 但是 MCP 天然支持 Oauth 认证，帮我们省去了这个环节

​	

* **没有客户隔离**

  如果 Agent 使用的是当前环境里已有的登录凭证，协议本身不会帮你区分不同公司之间的边界。

  也就是说，它不会天然知道：

  ```txt
  Acme 的数据只能进 Acme 的 Jira
  Globex 的数据只能进 Globex 的 Jira
  ```

  如果你自己写的“切换 token”代码出错，就可能把 Acme 的数据发到 Globex 的 Jira 里。这个问题不是普通程序 bug，而是严重的数据泄露。



* **没有用户授权流程**

  CLI 用的 token 通常是开发者自己生成的，不是终端用户通过一个正式授权页面授权出来的。

  但如果你的产品给客户使用，**客户员工应该有一个正式授权过程**，比如：

  ```txt
  这个 AI 助手想访问你的 GitHub
  权限范围：只读 PR、创建 issue
  是否同意？
  以后是否可以撤销？
  ```

  CLI token 本身不提供这种“用户同意 + 权限范围 + 可撤销”的流程。

  所以如果你硬用 CLI 做企业产品，就得自己做一堆认证授权功能。结果你本来想做 AI 产品，最后却变成在造 OAuth、token 管理和权限系统。



* **没有审计记录**

  没有完整的操作追踪记录。命令行的历史记录只能告诉你执行过什么命令，比如：

  ```bash
  gh pr merge
  gh issue create
  ```

  但它不会告诉你：

  ```txt
  是谁授权 Agent 执行的？
  这个人属于哪家公司？
  当时用了哪个用户的权限？
  这个操作有没有经过允许？
  ```

  如果 Acme 的安全团队追问：“到底是我们哪个员工触发了这次 GitHub 操作？”你很难从 CLI 协议本身给出可靠答案。

  企业客户通常不会接受这种不透明的系统。





## 这并不是理论上的问题

前面说的权限混乱、租户隔离、授权流程、审计记录这些问题，不是凭空想象出来的风险，而是真实生产环境里会发生、也必须认真解决的问题。

OpenClaw 这个例子说明了：**如果 CLI 型 Agent 没有底层协议级别的授权机制**，却被拿去支持多个用户，就会出问题：

* **有 1 万多个 OpenClaw 实例被暴露到了公网**，里面的登录凭证、API 密钥、会话 token 等敏感信息都可能被别人看到。（Bitsight）
* 研究发现，**社区里有 12% 的 skills 是有问题的恶意技能**。它们可能会偷偷插入代码、把你的数据传出去，或者在你的系统里留下后门，方便以后继续控制。（Astrix Security）
* 有一个真实安全漏洞影响了大量 Agent。攻击者不一定需要直接进入你的电脑，只要通过恶意网站，就可能接管 Agent 的会话。

这些问题不是因为 OpenClaw 某几行代码写错了，而是**因为它的架构本身有风险**：Agent 可以访问 shell，又能使用当前环境里的登录凭证，但中间缺少明确的权限边界。

CLI Agent 之所以快，是因为它：

```txt
直接用当前登录状态
可以执行任意命令
几乎没有协议层面的额外开销：意思是 CLI 不需要像 MCP 那样，在每次工具调用前后都携带大量额外结构化信息。
例如 MCP 可能需要把工具 schema 注入上下文，用来说明工具列表、参数类型、必填字段、调用格式、返回格式等；在企业场景里，还可能涉及权限范围、身份信息、租户边界等配套信息。
这些信息能让系统更标准、更可控，但也会增加 token 成本、延迟和系统复杂度。
```

但这些优点一旦放到多用户、客户使用、企业产品场景里，就会变成安全隐患。



# MCP 哪些地方是对的



## MCP 这些额外开销不是白花的，它换来了三个 CLI 做不到的能力。



* **每个用户单独授权**。通过 OAuth 2.1 + PKCE，每个用户都可以明确授权你的 Agent 访问哪些东西。比如用户可以知道：

  ```txt
  我授权了它读取 GitHub PR
  我授权了它创建 Jira 工单
  我没有授权它删除仓库
  ```

  用户之后也可以取消授权。更重要的是，**你的应用不需要直接拿到用户的密码或原始凭证**。

* **明确的工具边界**。Agent 只能用你提前声明好的工具，不能随便执行命令行。

  也就是说，它不能自己偷偷来一条：

  ```bash
  curl https://private-api.xxx.com
  ```

  去访问一个你没允许它访问的私有接口。

  每个操作都被提前定义好：能调用什么、参数是什么、权限范围是什么、结果大概是什么。这样系统行为更可控，也更容易防止 OpenClaw 那种安全问题。

* **结构化审计记录。** Agent 每调用一次工具，系统都会记录清楚：

  ```txt
  是谁授权的？
  它请求了什么？
  工具返回了什么？
  这个操作属于哪个用户？
  这个操作属于哪个公司？
  ```

  这不是简单的命令行历史记录，而是可以搜索、可以统计、可以追责的正式日志。



MCP 之所以花费更加昂贵，是因为它多做了很多事情：

```txt
明确说明工具怎么用
走 OAuth 授权流程
返回结构化结果
留下可追踪记录
```

但这些东西不是没用的负担。**正是因为有这些机制，MCP 才更容易被管理、审计和控制。**

如果你不用 MCP，而是用 CLI Agent，那这些权限、授权、日志、隔离能力，**最后也得你自己重新做一遍**。



# 决策框架

## 让使用方式与部署场景相匹配

不要简单问“CLI 好还是 MCP 好”，你应该先看你的 Agent 是怎么部署、给谁用的。

![图片2](/images/articles/hello-2.png)



* 如果你做的是给**开发者自己用的工具**，那就用 CLI + Skills。给 Agent 配一份大约 800 token 的工具使用小抄，就能获得测试里最好的效率。这个场景不需要复杂的“每个用户单独授权”，因为使用者就是开发者本人。
* 如果你做的是一个产品，**Agent 要替客户做事**，那你就需要 MCP 这类授权机制。但是，不要直接连那种暴露了 43 个工具的 MCP 服务器。因为前面已经证明了：这样成本会很高，稳定性也会变差。
* 如果你做的是**多客户、多公司使用的企业级系统**，那就不能只选 CLI 或只选 MCP。你需要 MCP 的授权体系来保证权限、安全、审计和治理；同时还需要加一层 gateway，把 MCP 暴露出来的工具和 schema 做过滤、优化，解决前面测试里看到的成本高、速度慢、不稳定问题。



# 架构

加一层 gateway 之后，你可以同时拿到两边的好处：

```txt
1. CLI 的高效率
2. MCP 的授权、安全和治理能力
```

![图片3](/images/articles/hello-3.png)



* **Schema 过滤。** 原本 MCP 可能会把 GitHub 的 43 个工具说明全部塞给 Agent。但有了 gateway 后，它只给当前任务真正需要的 2 到 3 个工具说明。比如你只是要查 PR，就只给：

  ```txt
  读取 PR 信息
  读取仓库信息
  列出评论
  ```

  而不会把创建 gist、配置 webhook、管理 review 等无关工具都塞进去。

  这样 token 从 44,000 左右降到 3,000 左右，省了大约 90%，效率就接近 CLI 了。

* **连接池**。原本每个 Agent 会话都要自己连接 MCP 服务器。连接多了之后，就容易遇到超时、断开、失败。有了 gateway 后，它会提前维护好一批长期连接。Agent 不用每次都重新连 MCP 服务器，而是**通过 gateway 复用已有连接。**这样可以减少连接超时问题，把失败率从 28% 左右降到大约 1%。

* **认证集中化。** 以前可能是每个 Agent 自己去管理 GitHub、Jira、Slack 的 token：

  ```txt
  Agent 管 GitHub token
  Agent 管 Jira token
  Agent 管 Slack token
  ```

  这样很乱，也容易出错。

  有了 gateway 后，token 刷新、权限检查、审计日志都集中在 gateway 里做。

这就是 Scalekit 现在正在做的系统架构。前面的测试数据让我们意识到：**这种架构确实有必要**。而且这些数据也告诉我们，应该重点优化哪些地方。
